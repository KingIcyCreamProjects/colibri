# Tuning notes — Ryzen 9 9950X3D + RTX 5090 (native Windows 11)

The reference box for the [KingIcyCreamProjects/colibri](https://github.com/KingIcyCreamProjects/colibri)
fork. Every number here is measured on this one machine; treat it as an engineering
datapoint, not a portable guarantee.

## The box

| Part | Detail |
|---|---|
| CPU | Ryzen 9 9950X3D (16C/32T, Zen5, **avx512-vnni**; V-cache on CCD0 = CPUs 0-15) |
| RAM | 64 GB DDR5-6000 |
| GPU | RTX 5090 (32 GB, Blackwell, compute capability **sm_120**); GTX 1660 Super unused |
| Storage | Samsung 9100 PRO 4TB, **PCIe Gen5** NVMe (NTFS, local, only drive) |
| OS / toolchain | Windows 11 x86-64, **MSYS2 UCRT64** gcc 16.1.0, **CUDA 13.3.1** + MSVC 14.44 for the DLL |

## Build

CPU engine, tuned for this CPU (the banner must confirm the kernel):

```bash
cd c
make glm CUDA_DLL=1 ARCH=native      # -> glm.exe; banner prints "idot: avx512-vnni"
```

`ARCH=native` selects the `avx512-vnni` integer-dot kernel (glm.c picks it when
`__AVX512VNNI__ && __AVX512BW__` are defined); the portable `x86-64-v3` default
would compile it out. `CUDA_DLL=1` links the runtime loader so `glm.exe` picks up
`coli_cuda.dll` via `LoadLibrary` if present, and falls back to CPU if not.

The CUDA backend is a separate `coli_cuda.dll` (nvcc + MSVC). `make cuda-dll
CUDA_ARCH=sm_120` builds it; the direct nvcc line it runs is:

```bash
# From c/, in a shell with the MSVC env set (vcvars64.bat) and nvcc on PATH:
nvcc -O3 -std=c++17 -arch=sm_120 -Xcompiler=-W3 -shared -DCOLI_CUDA_BUILDING_DLL \
  -L"$CUDA_HOME/lib/x64" -lcudart backend_cuda.cu -o coli_cuda.dll
```

`sm_120` must match the RTX 5090 (Blackwell). `-Xcompiler=-W3` is required because
nvcc's host compiler here is MSVC `cl.exe`, which rejects the GCC `-Wall,-Wextra`
default. CUDA 13.3 compiles `grouped_s4_wmma` for sm_120 without complaint.

Note: `make check` cleans and rebuilds portable — rebuild with `ARCH=native` and
re-run the nvcc line afterwards (`clean` deletes `coli_cuda.dll`).

## Disk baseline (iobench)

`iobench.exe` issues the same parallel 19 MB random reads the engine uses
(2.51 GB shard, measured while a background download wrote ~14 MB/s — ±5% noise):

| mode | threads | GB/s |
|---|---|---|
| O_DIRECT | 4 | **10.68** |
| O_DIRECT | 8 | 10.40 |
| O_DIRECT | 16 | 8.07 |
| O_DIRECT | 24 | 8.57 |
| O_DIRECT | 32 | 8.71 |
| buffered | 4 | 4.86 |
| buffered | 8 | 9.03 |
| buffered (warm, 2nd pass) | 8 | 8.99 |

Conclusions:
- **DIRECT=1 wins on bare Gen5 NVMe.** Buffered caps at ~9 GB/s even fully warm —
  the page-cache copy path is the bottleneck, not the drive. Use the O_DIRECT run
  (last arg `1`) for a true disk number; a buffered run on a big-RAM box reports
  the page cache, not the drive (#86).
- **Reader-thread knee ≤ 8**: throughput *degrades* past 8 readers. The default
  `PIPE_WORKERS=8` is right for this drive; a cap raise to 32 was rejected by
  this measurement.
- Windows page-cache readahead shims are moot under DIRECT (bypasses the cache).

## CUDA fixture benchmark

Before the real 370 GB model is in place, the deterministic 313M-parameter
`glm_moe_dsa` fixture exercises the real MLA/MoE/streaming shapes with random
weights (it is **not a language model** — tok/s here is fixed-token replay
throughput, not generation):

```bash
cd c
python tools/make_glm_bench_model.py --output C:\models\glm_bench --device cuda
python tools/benchmark_cuda_fixture.py --model C:\models\glm_bench --gpu 0 --threads 16
```

Measured on this box (medians):

| mode | tok/s | expert-matmul s | notes |
|---|---|---|---|
| cpu_stream | 7.7–8.4 | 0.82–0.87 | VNNI CPU path |
| dense_cuda | 6.8–7.7 | 0.86–0.98 | `CUDA_DENSE=1` **negative** at fixture scale |
| cpu_pin | 8.5–9.4 | 0.81–0.89 | RAM-resident experts |
| **cuda_pin** | **152–162** | **0.010–0.012** | VRAM-resident experts ≈ free compute |
| cuda_pin_dense | 116–125 | 0.008–0.009 | dense-on-GPU again negative |

The cuda_pin row isolates the CUDA hot-expert kernel from disk: with experts
resident on the 5090, expert FFN cost collapses ~80× vs the already-VNNI CPU path.
On the real model this applies only to the `CUDA_EXPERT_GB` slice that fits in
VRAM, so its end-to-end value scales with the VRAM hit rate — maximize the tier
and warm the usage profile. `CUDA_DENSE=1` must be re-A/B'd at real 10 GB dense
scale before trusting the fixture's negative.

## Recommended Windows env

```powershell
$env:PIPE="1"        # overlap expert disk-load with matmul (byte-identical output)
$env:DIRECT="1"      # O_DIRECT/unbuffered expert reads (Gen5 NVMe likes this)
$env:MLOCK="1"       # wire the pinned expert tier into RAM (VirtualLock)
python coli chat --model C:\models\glm52_i4
```

The `coli` launcher already sets the OpenMP hot-team tuning on Windows
(`OMP_WAIT_POLICY=active`, `GOMP_SPINCOUNT`, `OMP_DYNAMIC=FALSE`,
`OMP_NUM_THREADS=<physical cores>`) unless `COLI_NO_OMP_TUNE=1`. It deliberately
does **not** set `OMP_PROC_BIND`/`OMP_PLACES`: MinGW libgomp has no affinity
support on Windows ("Affinity not supported on this configuration"). To pin a run
to the V-cache CCD, use whole-process affinity instead:
`cmd /c start /wait /affinity 0xFFFF ...` (CPUs 0-15). `PIPE_WORKERS` defaults
to 8 and only matters when `PIPE=1`.

## Fork patches measured/validated on this box

- `resource_plan`: physical-core count on Windows (was 32 logical → 16 physical).
- `coli`: Windows OMP tuning env parity (WAIT_POLICY/SPINCOUNT/DYNAMIC/threads).
- `Makefile`: CUDA_ARCH=native pitfall documented (+ sm_120 example).
- `benchmark_cuda_fixture`: parser fixed for the current PROFILE service/wait format.
- Rejected by measurement: PIPE_WORKERS cap raise, Windows page-cache readahead shim.
- Not needed: s4-WMMA Blackwell guard — CUDA 13.3 builds it for sm_120 fine.

Bottom line: **0.45 → 1.25 tok/s (2.8×) at the 96-token benchmark, ~1.1 tok/s
sustained at 256 tokens, from configuration alone** — no engine code changes.
Winning stack: launcher defaults (OMP block + `DIRECT=1` + `PIPE=1` +
`PILOT_REAL=1`) plus CUDA env
(`COLI_CUDA=1 COLI_GPU=0 CUDA_EXPERT_GB=24 REPIN=16 CUDA_DENSE=1 COLI_CUDA_ATTN=1`).
Speculation (`DRAFT`) stays off — which is already the engine default under CUDA.

MTP/DRAFT and `--topp` are **not** exercised by REPLAY (it teacher-forces tokens
through `step()`, not `spec_decode()`) — those A/Bs use real 96-token greedy
generation with a fixed prompt instead.
