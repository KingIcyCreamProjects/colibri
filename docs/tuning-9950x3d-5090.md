# Tuning report: Ryzen 9 9950X3D + RTX 5090 + Samsung 9100 PRO (Windows 11 native)

Hardware: 9950X3D (16C/32T Zen 5, AVX-512-VNNI), 64 GB DDR5-6000, Samsung 9100 PRO 4TB
(Gen5 NVMe, only drive), RTX 5090 32 GB (sm_120, driver 610.74), GTX 1660 Super 6 GB (unused).
Toolchain: MSYS2 UCRT64 gcc 16.1.0, CUDA Toolkit 13.3.1 (V13.3.73), MSVC 14.44.
Build: `make glm CUDA_DLL=1 ARCH=native` → banner `idot: avx512-vnni`; DLL:
`nvcc -O3 -std=c++17 -arch=sm_120 -Xcompiler=-W3 -shared -DCOLI_CUDA_BUILDING_DLL ... backend_cuda.cu -o coli_cuda.dll`
(CUDA 13.3 compiles `grouped_s4_wmma` for sm_120 without complaint.)

All numbers single-machine engineering measurements, taken while a background
HF download wrote ~14 MB/s to the same drive — treat ±5% as noise.

## iobench (19 MB blocks × 64, expert-read pattern, 2.51 GB shard)

| mode | threads | GB/s |
|---|---|---|
| O_DIRECT | 4 | **10.68** |
| O_DIRECT | 8 | 10.40 |
| O_DIRECT | 16 | 8.07 |
| O_DIRECT | 24 | 8.57 |
| O_DIRECT | 32 | 8.71 |
| buffered | 4 | 4.86 |
| buffered | 8 | 9.03 |
| buffered (warm, 2nd pass) | 8 | 8.99 |

Conclusions:
- **DIRECT=1 wins on bare Gen5 NVMe** (as the code comments predicted for real
  hardware vs the VHDX the default was tuned on). Buffered caps at ~9 GB/s even
  fully warm — the page-cache copy path is the bottleneck, not the flash.
- **Thread knee ≤ 8**: throughput *degrades* past 8 readers. `PIPE_WORKERS=8`
  (default) is right for this drive; raising the cap 16→32 (patch idea P4) is
  rejected by measurement.
- Page-cache readahead shim for Windows (patch idea P3) is moot under DIRECT.

## CUDA fixture A/B (313M random-weight GLM-shape fixture, 16 threads, medians of 7)

| mode | median tok/s | expert-matmul s | notes |
|---|---|---|---|
| cpu_stream | 8.43 | 0.821 | VNNI CPU path |
| dense_cuda | 7.72 | 0.859 | CUDA_DENSE=1 **hurts** at this scale |
| cpu_pin | 9.42 | 0.812 | RAM-resident experts |
| **cuda_pin** | **161.79** | **0.010** | VRAM-resident experts, 82× matmul speedup |
| cuda_pin_dense | 124.72 | 0.008 | dense-on-GPU again negative |

Conclusions:
- **The VRAM expert tier is the star on this GPU** — when an expert is resident
  in VRAM its FFN cost collapses to ~zero vs the (already VNNI-tuned) CPU path.
  On the real 370 GB model this applies to whatever slice fits in
  `CUDA_EXPERT_GB` (~24-26 GB after reserve), so its end-to-end value scales
  with the VRAM hit rate — maximize it and warm the usage profile.
- `CUDA_DENSE=1` was *negative* on the fixture (transfer/launch overhead beats
  the tiny dense compute). Must be re-A/B'd on the real model where dense is
  ~10 GB/token of real work.

## Patches on this branch

- `resource_plan`: physical-core count on Windows (was 32 logical → 16 physical).
- `coli`: Windows OMP tuning env parity (WAIT_POLICY/SPINCOUNT/DYNAMIC/threads);
  PROC_BIND/PLACES omitted — MinGW libgomp has no affinity support on Windows.
- `Makefile`: CUDA_ARCH=native pitfall documented (+ sm_120 example).
- `benchmark_cuda_fixture`: parser fixed for the current PROFILE service/wait format.
- Rejected by measurement: PIPE_WORKERS cap raise (P4), Windows readahead shim (P3).
- Not needed: s4-WMMA Blackwell guard (P5) — CUDA 13.3 builds it for sm_120 fine.
