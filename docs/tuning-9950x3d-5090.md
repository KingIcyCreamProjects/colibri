# Tuning notes — Ryzen 9 9950X3D + RTX 5090 (native Windows 11)

The reference box for the [KingIcyCreamProjects/colibri](https://github.com/KingIcyCreamProjects/colibri)
fork. Every number here is measured on this one machine; treat it as an engineering
datapoint, not a portable guarantee.

## The box

| Part | Detail |
|---|---|
| CPU | Ryzen 9 9950X3D (16C/32T, Zen5, **avx512-vnni**) |
| GPU | RTX 5090 (32 GB, Blackwell, compute capability **sm_120**) |
| Storage | Samsung 9100 PRO, **PCIe Gen5** NVMe (NTFS, local) |
| OS / toolchain | Windows 11 x86-64, **MSYS2 UCRT64** (gcc), **CUDA 13.3** + MSVC for the DLL |

## Build

CPU engine, tuned for this CPU (the banner must confirm the kernel):

```bash
cd c
make glm CUDA_DLL=1 ARCH=native      # -> glm.exe; banner prints "idot: avx512-vnni"
```

`ARCH=native` selects the `avx512-vnni` integer-dot kernel (glm.c picks it when
`__AVX512VNNI__ && __AVX512BW__` are defined); the portable `x86-64-v3` default
would compile it out. `CUDA_DLL=1` links the runtime loader so `glm.exe` picks up
`coli_cuda.dll` via `LoadLibrary` if present, and falls back to CPU if not.

The CUDA backend is a separate `coli_cuda.dll` (nvcc + MSVC). `make cuda-dll
CUDA_ARCH=sm_120` builds it; the direct nvcc line it runs is:

```bash
# From c/, in a shell with the MSVC env set (vcvars64.bat) and nvcc on PATH:
nvcc -O3 -std=c++17 -arch=sm_120 -Xcompiler=-W3 -shared -DCOLI_CUDA_BUILDING_DLL \
  -L"$CUDA_HOME/lib/x64" -lcudart backend_cuda.cu -o coli_cuda.dll
```

`sm_120` must match the RTX 5090 (Blackwell). `-Xcompiler=-W3` is required because
nvcc's host compiler here is MSVC `cl.exe`, which rejects the GCC `-Wall,-Wextra`
default.

## Disk baseline (iobench)

`iobench.exe` issues the same parallel 19 MB random reads the engine uses. On this
box's Gen5 NVMe, the O_DIRECT path (compat.h maps it to `FILE_FLAG_NO_BUFFERING`
on Windows) measured:

```bash
./iobench.exe /path/to/glm52_i4/out-00069.safetensors 19 64 8 1   # O_DIRECT
# -> ~10.7 GB/s
```

Use the O_DIRECT run (last arg `1`) for a true disk number — a buffered run on a
big-RAM box reports the page cache, not the drive (#86). At ~10.7 GB/s the drive
is fast enough that decode becomes **matmul-bound** rather than disk-bound once the
cache warms, which is the regime the recommended env below targets.

## CUDA fixture benchmark

Before the real 370 GB model is in place, the deterministic 313M-parameter
`glm_moe_dsa` fixture exercises the real MLA/MoE/streaming shapes with random
weights (it is **not a language model** — the tok/s here are fixed-token replay
throughput, not generation quality):

```bash
cd c
python tools/make_glm_bench_model.py --output /nvme/colibri-bench-medium --device cuda
python tools/benchmark_cuda_fixture.py --model /nvme/colibri-bench-medium --gpu 0
```

Measured on this box:

| fixture path | replay tok/s |
|---|---|
| CPU streaming (avx512-vnni) | 8–9 |
| CUDA hot-expert (pinned in VRAM) | **152–162** |

This is the fixture's shape-replay speed with all experts resident on the 5090, not
a real-model rate — it isolates the CUDA hot-expert kernel from disk. Real-model
decode is bounded by expert streaming and is far lower (see the honest-numbers
sections in the README).

## Recommended Windows env

```powershell
$env:PIPE="1"        # overlap expert disk-load with matmul (byte-identical output)
$env:DIRECT="1"      # O_DIRECT/unbuffered expert reads (Gen5 NVMe likes this)
$env:MLOCK="1"       # wire the streamed expert cache into RAM
python coli chat --model D:\glm52_i4
```

The `coli` launcher already sets the OpenMP hot-team tuning
(`OMP_WAIT_POLICY=active` + proc-bind) unless `COLI_NO_OMP_TUNE=1`; on this
disk-then-matmul-bound box, leave it on. `PIPE_WORKERS` defaults to 8 and only
matters when `PIPE=1` — tune it to the drive if you over/under-subscribe cores.
